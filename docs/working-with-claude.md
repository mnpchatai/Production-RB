# ข้อควรระวังเวลาใช้ Claude Code กับงานประเภทนี้

1. **อย่าให้เขียน schema ทั้งระบบในครั้งเดียว** โมเดลจะสร้างตารางที่ดูสมเหตุสมผล
   แต่ขาดรายละเอียดที่มีผลจริง เช่น effective date ของ BOM หรือ idempotency key
   ให้ทำทีละเฟสแล้วตรวจ

2. **ระวังคอลัมน์ยอดคงเหลือที่แอบโผล่มา** เป็นรูปแบบที่พบบ่อยมากในโค้ดที่โมเดลสร้าง
   เพราะมันเร็วและตรงไปตรงมา ให้ตรวจด้วย `/check-invariants` ทุกครั้งก่อน merge

3. **เทสต์ที่โมเดลเขียนเองมักทดสอบเฉพาะเส้นทางที่ทำงานได้** ให้สั่งเขียนเทสต์
   สำหรับเส้นทางที่ต้องล้มเหลวด้วยเสมอ เช่น เบิกเกินสต็อก แก้ใบที่ปิดแล้ว ยิงซ้ำ

4. **ให้เสนอ migration ก่อนเสมอ** งานฐานข้อมูลย้อนกลับยากกว่างานโค้ดมาก
   โดยเฉพาะเมื่อขึ้นระบบจริงแล้ว

5. **ข้อมูลจริงจากโรงงานคือสิ่งที่ต้องเอาเข้ามาเทสต์เร็วที่สุด** BOM จริงสัก 10 รายการ
   ที่ซับซ้อนที่สุดจะเปิดเผยข้อบกพร่องของโครงสร้างได้มากกว่าข้อมูลตัวอย่างที่โมเดลสร้างขึ้น

6. **บันทึกการตัดสินใจไว้ใน `docs/decisions/`** เมื่อเลือกทางใดทางหนึ่งให้เขียนสั้นๆ
   ว่าเลือกอะไรเพราะอะไรและตัดทางไหนทิ้ง เพราะเซสชันใหม่ของ Claude Code จะไม่รู้เหตุผลเดิม
   และมีแนวโน้มจะเสนอให้ย้อนกลับไปทางที่คุณตัดทิ้งไปแล้ว

## รอบการทำงานที่ควรใช้ต่อหนึ่งเฟส

1. เปิดเซสชันใหม่ วาง prompt จาก `docs/phases/phase-N-*.md`
2. รอให้เสนอ migration ก่อน อ่านให้จบ แล้วค่อยยืนยัน
3. ให้เขียนเทสต์ก่อน implementation สำหรับทุกอย่างที่แตะสต็อกหรือต้นทุน
4. `/check-invariants`
5. `/pre-merge-review`
6. อัปเดตสถานะใน `docs/phases/README.md` และบรรทัดสุดท้ายของ `CLAUDE.md`

ข้ามข้อ 4 กับ 5 ไม่ได้ ต่อให้เฟสนั้นดูเล็ก — INVARIANT ที่หลุดในเฟสเล็ก
จะไปโผล่เป็นยอดสต็อกผิดในเฟสใหญ่

## สัญญาณว่าควรหยุดแล้วถามคน

- โมเดลเสนอให้เพิ่มคอลัมน์ยอดคงเหลือ "เพื่อความเร็ว"
- โมเดลเสนอให้ตั้ง `allow_negative = true` เพื่อแก้ปัญหาของไม่พอ
- โมเดลเสนอให้ข้ามเทสต์ concurrency เพราะ "ทดสอบยาก"
- โมเดลเสนอให้ย้อนกลับไปทางที่มี ADR ตัดทิ้งไปแล้ว โดยไม่อ้างถึง ADR นั้น

ทั้งสี่อย่างนี้ไม่ใช่ข้อผิดพลาดทางเทคนิค แต่เป็นการเลี่ยงข้อกำหนด
ซึ่ง CLAUDE.md ระบุไว้ว่าต้องหยุดถามก่อน
