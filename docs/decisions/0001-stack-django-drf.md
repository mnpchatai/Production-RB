# 0001 — เลือก Django + DRF + PostgreSQL + React

- สถานะ: ตกลงใช้
- วันที่: 2026-09-07
- เกี่ยวข้องกับ: ทุกเฟส

## บริบท

ต้องเลือก stack ก่อนเริ่มเฟส 0 ข้อกำหนดที่บีบการเลือกมากที่สุดคือ INVARIANT
ข้อ 3, 8 และ 10 — ยอดสต็อกคำนวณจากธุรกรรม, บันทึกผลหน้างานต้อง idempotent,
และทุกฟังก์ชันที่แตะสต็อกต้องอยู่ใน transaction เดียวพร้อมล็อกแถว

ระบบเดิมของแผนก RB เป็นหน้าเว็บเดียวคุยกับ Supabase ตรง ๆ ซึ่งไม่มีที่ทางให้
วาง service layer ที่ควบคุมสองข้อหลังได้

## ทางเลือกที่พิจารณา

**Django + DRF + Django ORM + PostgreSQL + React (เลือก)**
มี `transaction.atomic()` และ `select_for_update()` เป็นของมาตรฐานในภาษา
มี migration ในตัว มี service layer ชัดเจน ทดสอบ concurrency ด้วย thread จริงได้
ทีมมีโค้ด Python อยู่แล้วจากงาน ETL ของระบบเดิม (`etl.py`, `load.py`)
จึงไม่ต้องเรียนภาษาใหม่เพื่อย้ายข้อมูลเก่าเข้าระบบใหม่

**Supabase-first (Postgres + RLS + Edge Functions) — ตัดทิ้ง**
ต่อยอดจากระบบเดิมได้เร็วที่สุดและไม่ต้องดูแล backend เอง
แต่ business logic จะกระจายอยู่ใน SQL function กับ RLS policy ซึ่งขัดกับ
INVARIANT ข้อ 7 (state machine ที่เดียว) โดยตรง และการทดสอบ race condition
กับสถานการณ์ end-to-end แบบที่ `docs/scenarios.md` ต้องการทำได้ลำบากกว่ามาก

**NestJS + Prisma — ตัดทิ้ง**
ความสามารถด้าน transaction เทียบเท่า Django แต่ทีมไม่มีโค้ด TypeScript ฝั่ง
backend อยู่เดิม และ Prisma ยังต้องเลี่ยงไปเขียน raw SQL สำหรับ
`SELECT ... FOR UPDATE` ในหลายกรณี

**Go + sqlc — ตัดทิ้ง**
คุม SQL ได้ละเอียดที่สุด เหมาะกับแกนสต็อกมาก แต่โค้ดต่อฟีเจอร์มากกว่าทางอื่น
ชัดเจน และระบบนี้มีหน้าจอกับรายงานเยอะ ไม่ใช่ระบบที่ปริมาณธุรกรรมสูงจน
ต้องแลกด้วยความเร็วในการพัฒนา

## ผลที่ตามมา

- ต้องดูแล backend เองแทนที่จะพึ่ง Supabase — แลกมากับการควบคุม transaction
  และ state machine ที่ INVARIANT บังคับ
- เทสต์ต้องรันบน PostgreSQL จริงเท่านั้น ห้าม SQLite เพราะ `select_for_update`
  และ `numeric` ทำงานไม่เหมือนกัน — CI ต้องมี Postgres service
- ยังใช้ Supabase เป็นที่ host PostgreSQL ได้ ถ้าจะทำเช่นนั้นต้องปิด
  การเข้าถึงตารางตรงจาก client ทั้งหมด ให้ผ่าน API ทางเดียว มิฉะนั้น
  INVARIANT ข้อ 7 และ 10 จะถูกข้ามได้จากฝั่งหน้าเว็บ

## เงื่อนไขที่ต้องกลับมาทบทวน

ถ้าปริมาณธุรกรรมสต็อกเกินราวหนึ่งแสนรายการต่อวัน หรือ `post_transaction`
กลายเป็นคอขวดจากการล็อกแถว ให้ทบทวนเฉพาะส่วนนั้น (แยกเป็นบริการต่างหาก
หรือย้ายไป Go) ไม่ใช่รื้อทั้งระบบ
