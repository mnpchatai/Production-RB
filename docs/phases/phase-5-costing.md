# เฟส 5 — ต้นทุนและรายงาน

```
งาน: คิดต้นทุนจริงต่อใบสั่งผลิต และรายงานติดตาม

ต้นทุนจริง = วัตถุดิบที่เบิกจริง (ตาม stock_transaction)
           + ค่าแรงจากชั่วโมงที่บันทึกจริง x อัตราของ work_center
           + overhead ตามฐานที่กำหนด

ข้อกำหนด: ต้องเปิดดูได้ว่าต้นทุนแต่ละก้อนมาจากธุรกรรมใบไหนบ้าง
(drill down ถึงระดับ stock_transaction)

รายงาน:
1. สถานะใบสั่งผลิตทั้งหมด แยกตามขั้นตอนที่ค้าง
2. เทียบต้นทุนตามแผนกับต้นทุนจริง แสดงส่วนต่างแยกเป็นวัตถุดิบ/ค่าแรง
3. ของเสียแยกตามสาเหตุและ work center
4. ใบสั่งขายที่เสี่ยงส่งไม่ทัน
```

## drill down คือข้อกำหนดโครงสร้าง ไม่ใช่ฟีเจอร์ UI

ต้นทุนทุกก้อนต้องชี้กลับไปยังแถวต้นทางได้ แปลว่า **ห้ามคำนวณต้นทุนแล้วเก็บแต่ยอดรวม**
ทุกยอดรวมต้องมีวิธีกางเป็นรายบรรทัดจาก `stock_transactions` (วัตถุดิบ) หรือ
`work_order_operations` (ค่าแรง) ได้เสมอ

ถ้าเก็บยอดรวมไว้เพื่อความเร็ว ต้องสร้างใหม่จากศูนย์ได้ และต้องมีเทสต์ที่
สร้างใหม่แล้วเทียบว่าตรงกับค่าที่เก็บไว้ (เจตนารมณ์เดียวกับ INVARIANT ข้อ 3)

## อัตราค่าแรงและ overhead มีวันเริ่มมีผล

`work_centers.labor_rate` **ห้ามเป็นค่าเดียวที่แก้ทับได้** — ถ้าแก้อัตราวันนี้
ต้นทุนของ WO ที่ปิดไปเมื่อเดือนที่แล้วจะเปลี่ยนย้อนหลัง ซึ่งบัญชีรับไม่ได้

ต้องเป็นตาราง `work_center_rates` ที่มี `effective_from` / `effective_to`
แบบเดียวกับ BOM (INVARIANT ข้อ 9 ในทางปฏิบัติ) และการคิดต้นทุนต้องอ้าง
อัตราตามวันที่ของธุรกรรม ไม่ใช่อัตราปัจจุบัน

overhead เหมือนกัน: ฐานการปันส่วน (ชั่วโมงเครื่อง / ชั่วโมงคน / มูลค่าวัตถุดิบ)
ต้องเลือกและเขียน ADR แล้วเก็บอัตราแบบมีช่วงเวลามีผล

## ต้นทุนตามแผนมาจากไหน

รายงานข้อ 2 เทียบแผนกับจริง — "แผน" ต้องมาจาก **snapshot ใน WO** เท่านั้น
(`work_order_materials.qty_required` × ราคามาตรฐาน ณ วันที่ออกใบ +
`work_order_operations` × อัตราของ work center ณ วันที่ออกใบ)

ห้ามคำนวณแผนใหม่จาก BOM ปัจจุบัน — นั่นละเมิด INVARIANT ข้อ 2 ตรง ๆ
และทำให้ variance เปลี่ยนไปเรื่อย ๆ ทุกครั้งที่มีคนแก้ BOM

แปลว่า **เฟส 2 ต้อง snapshot ราคามาตรฐานไว้ด้วย** ถ้าเฟส 2 ไม่ได้เก็บ
ต้องกลับไปเพิ่มพร้อม migration และ backfill ไม่ใช่ประมาณเอาจากราคาปัจจุบัน

## รายงานที่ 4 — ใบสั่งขายที่เสี่ยงส่งไม่ทัน

ต้องนิยาม "เสี่ยง" ให้ชัดและเขียนไว้ในโค้ด ไม่ใช่ให้แต่ละคนตีความ
เกณฑ์เริ่มต้นที่ใช้ได้:

- WO ที่ผูกกับ SO line ยังไม่ `completed` และ
- `due_date` ของ SO line ลบด้วยวันนี้ น้อยกว่าเวลาที่เหลือตาม routing
  (ผลรวม `run_minutes_per_unit` × จำนวนที่ยังไม่เสร็จ + `setup_minutes` ของขั้นที่ยังไม่เริ่ม)

แสดงจำนวนวันที่ขาดด้วย ไม่ใช่แค่ธง "เสี่ยง/ไม่เสี่ยง" — ฝ่ายวางแผนต้องเรียงลำดับได้

## ประสิทธิภาพ

รายงานทั้งสี่ห้ามยิงคิวรีในลูป ทุกตัวควรเป็นคิวรีเดียวหรือไม่กี่คิวรี
ถ้าช้า ให้ใช้ materialized view ที่รีเฟรชตามรอบ **ไม่ใช่** คอลัมน์สรุปที่เขียนทับได้
