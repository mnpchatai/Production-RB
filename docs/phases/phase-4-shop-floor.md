# เฟส 4 — บันทึกผลหน้างาน

```
งาน: API และหน้าจอสำหรับบันทึกผลหน้างานบนแท็บเล็ต

API: POST /shop-floor/report
body: { client_ref, wo_no, operation_seq, qty_good, qty_scrap,
        scrap_reason_code?, started_at?, finished_at? }

ระบบต้องเติมให้เอง ห้ามรับจาก client: user, work_center, shift,
เวลามาตรฐาน, ต้นทุน

พฤติกรรม:
- อัปเดต work_order_operations
- ถ้าเป็นขั้นตอนสุดท้าย ให้สร้างธุรกรรม wo_output รับสินค้าเข้าคลัง
- ตัดวัตถุดิบตาม BOM snapshot (backflush) พร้อมธงว่าเป็นการตัดอัตโนมัติ
- ถ้าวัตถุดิบไม่พอ ห้ามบล็อกการบันทึก ให้บันทึกไว้พร้อม exception flag
  แล้วส่งเข้าคิวให้ฝ่ายวางแผนตามแก้

หน้าจอ:
- ปุ่มขนาดใหญ่ ใช้งานได้ด้วยถุงมือ เป้าหมายบันทึกจบใน 15 วินาที
- ช่องจำนวนเติมค่ายอดคงเหลือตามแผนไว้ให้ก่อน
- รหัสสาเหตุของเสียแสดงเป็นปุ่มไม่เกิน 8 ปุ่ม
- รองรับออฟไลน์: เก็บคิวไว้ใน IndexedDB แล้ว sync ด้วย client_ref เดิม
```

## จุดที่ขัดกันเองและต้องแก้ให้ชัด

**"วัตถุดิบไม่พอห้ามบล็อก" ปะทะ "ห้ามยอดติดลบ" (INVARIANT ข้อ 3 + เฟส 3)**

ทางออกที่ระบบนี้ใช้: การบันทึกผลหน้างานกับการตัดวัตถุดิบเป็นคนละธุรกรรม

1. บันทึกผล (`work_order_operations` + `qty_good`/`qty_scrap`) — สำเร็จเสมอ
2. backflush ตัดวัตถุดิบ — ถ้าของไม่พอ ธุรกรรมสต็อกไม่เกิด
   แต่บันทึก `backflush_exceptions` ไว้พร้อม `client_ref` เดิม
   แล้วส่งเข้าคิวฝ่ายวางแผน
3. ฝ่ายวางแผนแก้ยอดแล้วสั่ง retry — ตัดจาก `backflush_exceptions` ด้วย
   `client_ref` เดิม จึงไม่เกิดการตัดซ้ำ

แปลว่า **ยอดสต็อกไม่ติดลบ** และ **หน้างานไม่ถูกบล็อก** พร้อมกันได้
สิ่งที่ยอมรับคือ "ยอดที่ตัดค้าง" ซึ่งมองเห็นได้ในคิว ไม่ใช่หายไปเงียบ ๆ

ห้ามแก้ปัญหานี้ด้วยการตั้ง `allow_negative = true` ให้วัตถุดิบทุกตัว

## ห้ามรับจาก client — บังคับยังไง

serializer ต้องไม่มีฟิลด์เหล่านี้เลย ไม่ใช่มีแล้ว ignore
ฟิลด์ที่ไม่รู้จักต้อง raise (`unknown fields` → 400) ไม่ใช่ปล่อยผ่านเงียบ ๆ

- `user` ← จาก token
- `work_center` ← จาก `work_order_operations.work_center_id` ของ `operation_seq` นั้น
- `shift` ← คำนวณจาก `posted_at` + ตารางกะ
- เวลามาตรฐาน ← จาก snapshot ใน `work_order_operations`
- ต้นทุน ← เฟส 5 คำนวณ ไม่มีใครส่งเข้ามา

`started_at` / `finished_at` รับได้ (หน้างานออฟไลน์ส่งย้อนหลัง)
แต่ต้อง validate ว่าไม่อยู่ในอนาคต และไม่เก่ากว่าวันที่ WO ถูก release

## ออฟไลน์

- คิวใน IndexedDB เก็บ `client_ref` ที่ **สร้างตอนกดปุ่ม** ไม่ใช่ตอนส่ง
  ถ้าสร้างตอนส่ง การ retry จะได้ uuid ใหม่ทุกครั้ง = ธุรกรรมซ้ำ
- ส่งเรียงตามลำดับที่บันทึก ไม่ส่งขนานกัน
- รายการที่ server ตอบ 4xx (ไม่ใช่ 5xx/timeout) ต้องหยุด retry
  และแสดงให้พนักงานเห็น ไม่ใช่วนซ้ำไม่รู้จบ
- แสดงจำนวนรายการค้างในคิวบนหน้าจอตลอดเวลา

## สองคนบันทึกขั้นตอนเดียวกันพร้อมกัน

ไม่ใช่ error — สองคนอาจทำงานคนละเครื่องในขั้นตอนเดียวกันจริง
`qty_good` ต้องเป็นการ **บวกสะสม** ผ่าน `select_for_update()` บนแถว
`work_order_operations` ไม่ใช่การเขียนทับค่า
ถ้าเขียนทับ ผลของคนหนึ่งจะหายไปโดยไม่มีใครรู้

## เกณฑ์หน้าจอ

"บันทึกจบใน 15 วินาที" เป็นข้อกำหนดที่ทดสอบได้ ไม่ใช่คำโฆษณา
ก่อนปิดเฟส ให้จับเวลาจริงกับเส้นทางที่ใช้บ่อยที่สุด (บันทึกของดีอย่างเดียว ไม่มีของเสีย)
ถ้าเกิน 15 วินาที ให้ลดจำนวนการกดก่อน ไม่ใช่ลดขนาดปุ่ม
