# ระบบ MES/MRP โรงงานยาง (Rubber Manufacturing Suite)

เว็บแอปหน้าเดียวภาษาไทยสำหรับโรงงานผลิตชิ้นส่วนยาง ครอบคลุมตั้งแต่เปิดใบสั่งผลิต
บันทึกผลผลิตรายวัน วัด OEE ของเครื่องจักร ไปจนถึงคำนวณความต้องการวัสดุ (MRP)
และออกใบสั่งซื้อ

เปิดไฟล์ `index.html` ผ่าน https หรือ localhost ได้เลย ไม่ต้อง build ไม่ต้องติดตั้งอะไร
รหัสผ่านเริ่มต้นคือ `rubber2026` (เปลี่ยนได้ที่ ตั้งค่าข้อมูลหลัก → ตั้งค่าทั่วไป)

> ต้องเปิดผ่าน https หรือ localhost เท่านั้น — หน้าล็อกอินใช้ `crypto.subtle`
> ซึ่งเบราว์เซอร์ปิดไว้บน `file://` ถ้าเปิดไฟล์ตรง ๆ จะขึ้นข้อความบอกไว้ให้

## สถาปัตยกรรม

ทั้งระบบอยู่ในไฟล์ `index.html` ไฟล์เดียว — vanilla JS ไม่มี framework ไม่มี build step
เหมือนแอปตัวอื่นในตระกูลเดียวกัน (`Grinding-GR`, `Maintanance-MT`)

```
index.html
├── <style>   design system (ธีมมืด accent ส้ม #e8792b / ฟ้า #3fb3c9)
├── <script src=cdn.jsdelivr.net/npm/chart.js@4.4.4>   กราฟ (มี fallback ถ้าโหลดไม่ได้)
└── <script>  แอปทั้งหมด
    ├── DB              ข้อมูลทั้งก้อน เก็บใน localStorage คีย์ rb_mes_db
    ├── state           สถานะ UI (หน้าที่เปิดอยู่, ตัวกรอง, โมดัล, ผล MRP)
    ├── render()        ยัด innerHTML ใหม่ทั้งหน้าทุกครั้งที่ state เปลี่ยน
    ├── VIEWS[route]    ฟังก์ชันคืน HTML ของแต่ละหน้า
    ├── MODALS[type]    ฟังก์ชันคืน {title, body, foot} ของแต่ละโมดัล
    ├── business logic  onHand / explodeBom / runMrp / oeeOf
    └── RBDATA          ข้อมูลจริงจาก Supabase (ตาราง rb_*) — อ่านอย่างเดียว แยกจาก DB
```

### render() และการรักษาโฟกัส

`render()` สร้าง DOM ใหม่ทั้งหมด ทำให้ช่องกรอกที่เรียก `render()` ตอน `oninput`
จะเสียโฟกัสทุกตัวอักษร แก้ด้วยแอตทริบิวต์ `data-fid="ชื่อเฉพาะ"` — ก่อนรื้อ DOM
`renderNow()` จะจำ `data-fid` กับตำแหน่งเคอร์เซอร์ของ element ที่โฟกัสอยู่แล้วคืนให้หลังสร้างใหม่

**ช่องกรอกใหม่ที่ `oninput` เรียก `render()` ต้องมี `data-fid` เสมอ ไม่งั้นพิมพ์ได้ทีละตัว**

### การเก็บข้อมูล

ตอนนี้ทุกอย่างอยู่ใน `localStorage` ของเบราว์เซอร์เครื่องนั้น ๆ (`saveDB()` เขียนแบบหน่วง 350 ms)
ล้างข้อมูลเบราว์เซอร์แล้วข้อมูลหายถาวร — หน้า ตั้งค่าข้อมูลหลัก → ข้อมูลระบบ มีปุ่มสำรอง/กู้คืน JSON ไว้ให้

ถ้าจะต่อ Google Apps Script + Google Sheet แบบเดียวกับ `Maintanance-MT`:
ช่อง `settings.apiUrl` มีอยู่แล้วในหน้าตั้งค่า เหลือแค่เปลี่ยน `loadDB()`/`saveDB()`
ให้ `fetch` ไปที่ URL นั้นแทน โดยต้องใช้ `Content-Type: text/plain;charset=utf-8`
(Apps Script ไม่มี `doOptions` — ถ้าส่งเป็น `application/json` จะโดน CORS preflight แล้วเงียบไปเฉย ๆ)

### ข้อมูลจริงจาก Supabase (คนละชุดกับ DB)

`RBDATA` เป็นอีกชุดข้อมูลแยกจาก `DB` อ่านตาราง `rb_*` บน Supabase ผ่าน PostgREST ตรง ๆ
(`fetch` ไม่ผ่านไลบรารี) ไล่ทีละหน้าหน้าละ 1000 แถวเพราะ PostgREST ตัดที่ 1000
ตาราง BOM มีเจ็ดพันกว่าแถว โหลดครั้งเดียวแล้วเก็บไว้ในหน่วยความจำ ไม่เขียนกลับ

ค่าเชื่อมต่อ (Project URL + anon key) เก็บใน `localStorage` คีย์ `rb_supabase_cfg`
**ไม่ได้ฝังในไฟล์** เพราะ repo เป็น public — ตั้งค่าที่ ตั้งค่าข้อมูลหลัก → Supabase (ข้อมูลจริง)

schema เปิด RLS ไว้ ต้องรัน `supabase/rb_planning/policies.sql` แล้วล็อกอินด้วยผู้ใช้
Supabase ในหน้าตั้งค่าก่อน ถึงจะอ่านข้อมูลได้ — access token เก็บที่คีย์ `rb_supabase_token`

วิธีย้ายข้อมูลจากไฟล์ Excel ขึ้น Supabase อยู่ที่ [`supabase/rb_planning/README.md`](supabase/rb_planning/README.md)

## ตรรกะสำคัญ

### ยอดคงคลัง

ไม่เก็บยอดสรุปไว้ที่ไหนเลย — `onHand(code)` รวมจาก `DB.txns` ทุกครั้ง (มี cache ในรอบ render)
ทำให้ยอดตรงกับรายการเคลื่อนไหวเสมอ ไม่มีทาง desync

ประเภทรายการ: `RECEIPT` รับเข้า (+), `ISSUE` เบิกผลิต (−), `PRODUCE` รับจากผลิต (+),
`SCRAP` ตัดของเสีย (−), `ADJUST` ปรับยอด (ใช้ค่าตามที่กรอก บวกหรือลบก็ได้)

### บันทึกผลผลิตหนึ่งครั้ง สร้างรายการคลังพร้อมกันหลายบรรทัด

ผลผลิตทั้งกอง (ของดี + ของเสีย) ถูก `PRODUCE` เข้าคลังก่อน แล้วค่อย `SCRAP` ของเสียออก
**ยอดสุทธิที่เพิ่มจึงเท่ากับของดีพอดี** ส่วนวัตถุดิบชั้นแรกตาม BOM ถูก `ISSUE` ตามจำนวนที่ผลิตจริง
(รวมของเสีย เพราะวัตถุดิบถูกใช้ไปแล้ว)

การลบบันทึกผลผลิตจะสร้างรายการ `ADJUST` ย้อนกลับ ไม่ลบรายการเดิมทิ้ง — ประวัติจึงตรวจสอบย้อนหลังได้

### MRP

`runMrp()` ทำตามขั้นตอนมาตรฐาน:

1. คำนวณ **low-level code** ของทุกรายการ แล้วไล่คำนวณจากชั้นบนลงชั้นล่าง
2. แบ่งเวลาเป็นถัง (ค่าเริ่มต้น 8 ถัง × 7 วัน = 56 วัน)
3. **ความต้องการ** มาจากใบสั่งผลิตที่ยังเปิดอยู่ (ระเบิด BOM ณ วันเริ่มงาน) + ความต้องการที่ผู้ใช้ป้อนจำลองเพิ่ม
4. **ของที่จะเข้า** มาจากใบสั่งซื้อที่ยังไม่รับครบ (ตาม ETA) และใบสั่งผลิตที่ยังไม่ปิด (ตามกำหนดเสร็จ)
5. ไล่ทีละถัง: `คงเหลือ = ยกมา + จะเข้า + แผนสั่ง − ความต้องการ`
   ถ้าต่ำกว่าสต็อกกันชนก็ออก planned order ปัดขึ้นตามขนาดล็อต
6. **วันออกใบสั่ง** = วันที่ต้องใช้ ถอยหลังด้วย lead time โดยนับเฉพาะวันทำงานตามปฏิทินโรงงาน
   ถ้าถอยแล้วเลยวันนี้ไปแล้ว รายการนั้นถูกทำเครื่องหมาย "ต้องสั่งย้อนหลัง" (สั่งวันนี้ก็ไม่ทัน)
7. planned order ของที่ผลิตเอง จะกลายเป็นความต้องการของลูกใน BOM ในถังของวันออกใบสั่ง

กดสร้างเอกสารจริงจากแผนได้ทันที — รายการซื้อของผู้ขายเดียวกันถูกรวมเป็นใบสั่งซื้อใบเดียว

### OEE

```
OEE = ความพร้อมเดินเครื่อง × ประสิทธิภาพ × คุณภาพ
ความพร้อมเดินเครื่อง = (เวลาที่วางแผน − เวลาหยุด) ÷ เวลาที่วางแผน
ประสิทธิภาพ         = เวลาที่ควรใช้ผลิตของที่ทำได้ ÷ เวลาเดินเครื่องจริง
คุณภาพ              = ของดี ÷ (ของดี + ของเสีย)
```

**เวลาที่วางแผนนับเฉพาะวันที่เครื่องนั้นมีบันทึกผลผลิตจริง** ไม่ใช่ทุกวันทำงาน —
ถ้านับวันที่ไม่มีงานเข้าเครื่องด้วย เวลาว่างจะไปโผล่เป็น "ประสิทธิภาพต่ำ" ทั้งกระดาน
ทั้งที่เป็นเรื่องการรับงาน ไม่ใช่ประสิทธิภาพเครื่อง เครื่องที่ไม่มีงานเลยในช่วงที่เลือกจะแสดงว่า
"ไม่มี OEE ให้วัด" แทนที่จะโชว์ 0%

### ข้อกันพลาดที่ใส่ไว้

- เปลี่ยนสถานะใบสั่งผลิตข้ามขั้นไม่ได้ (ต้องเดินตาม `WO_STATUS[x].next`)
- ปิดงานที่ยังไม่มีการบันทึกผลผลิตไม่ได้
- ลบใบสั่งผลิตที่มีบันทึกผลผลิตแล้วไม่ได้ (ให้ใช้การยกเลิกแทน)
- เพิ่มบรรทัด BOM ที่ทำให้สูตรวนกลับมาหาตัวเองไม่ได้ (`bomHasCycle` ไล่ตรวจทุกชั้น)
- ลบข้อมูลหลักที่ยังถูกอ้างถึงอยู่ไม่ได้ ระบบจะบอกว่าติดอยู่ที่ไหน
- รับของเกินจำนวนที่ค้างรับในใบสั่งซื้อไม่ได้
- ผลิตเกินยอดสั่งต้องกดยืนยันซ้ำอีกครั้ง

## ข้อมูลตัวอย่าง

เปิดครั้งแรกระบบสร้างข้อมูลตัวอย่างของโรงงานยางให้อัตโนมัติ (สุ่มแบบมี seed จึงได้ชุดเดิมทุกครั้ง):
สินค้า 18 รายการ 3 ชั้น (วัตถุดิบ → คอมพาวด์ → แผ่นรีด → บล็อกปั๊ม → สินค้าสำเร็จรูป),
สูตร BOM 20 บรรทัด, เครื่องจักร 12 เครื่อง 8 แผนก, ใบสั่งผลิตย้อนหลัง 20 วันถึงล่วงหน้า 1 เดือน,
บันทึกผลผลิตพร้อมของเสีย, เวลาเครื่องหยุด และใบสั่งซื้อค้างรับ

ขนาดใบสั่งผลิตตั้งจากกำลังผลิตเต็มกะของสินค้านั้น (อัตราผลิต × 8 ชม.) ไม่ได้สุ่มลอย ๆ
เพื่อให้ตัวเลข OEE ที่ออกมาสมจริง

ล้างหรือสร้างใหม่ได้ที่ ตั้งค่าข้อมูลหลัก → ข้อมูลระบบ

## การนำขึ้นใช้งาน

ไฟล์เดียวแบบ static ขึ้นได้ทั้ง GitHub Pages, Cloudflare Pages หรือเว็บเซิร์ฟเวอร์ทั่วไป
ชื่อไฟล์ต้องเป็น `index.html` ที่ root ของ repo

- **GitHub Pages** — Settings → Pages → Deploy from branch → เลือก branch แล้ว `/root`
- **Cloudflare Pages** — เชื่อม repo แล้วปล่อย build command ว่าง ตั้ง output directory เป็น `/`

## ข้อจำกัดที่ควรรู้

- **รหัสผ่านเป็นการกันคนเดินผ่าน ไม่ใช่ระบบความปลอดภัย** — hash เก็บฝั่งเบราว์เซอร์
  ใครเปิด DevTools ก็ข้ามได้ ข้อมูลจริงที่อ่อนไหวไม่ควรอยู่บน URL สาธารณะ
- **ข้อมูลแยกกันคนละเครื่อง** ยังไม่มี backend กลาง สองเครื่องเห็นข้อมูลคนละชุด
  ถ้าต้องใช้หลายคนพร้อมกันต้องต่อ backend ก่อน (ดูหัวข้อการเก็บข้อมูล)
- **localStorage จำกัดราว 5 MB** หน้าข้อมูลระบบแสดงขนาดปัจจุบันไว้ให้เฝ้าดู
- กราฟโหลดจาก CDN — ถ้าเน็ตเข้าไม่ถึง ระบบยังใช้งานได้ครบ เพียงแต่ช่องกราฟจะขึ้นข้อความแทน
- **หน้าข้อมูลจริงต้องล็อกอิน Supabase** — อย่าเปิด policy ให้ `anon` อ่านได้ ตราบใดที่หน้าเว็บ
  ยังอยู่บน URL สาธารณะ เพราะ anon key ฝังอยู่ในหน้าเว็บ ใครเปิด DevTools ก็เห็น
